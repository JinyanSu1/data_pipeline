# Change points, unknown count

You are given a collection of numeric series. Each series is piecewise
stationary: it is generated by one distribution for a stretch of samples, then
by a different one, and so on. Your job is to find the boundaries.

The hard part is not finding *a* boundary. It is deciding **how many there
are**, per series, when nobody tells you — and the answer is sometimes zero.

## Deliverable

Edit `/app/solution.py` so that it defines:

```python
def find_changepoints(series) -> list[int]:
    """series: list of rows (each row is a list of floats). Return sorted indices."""
```

* `series` is the whole series, offline. You may look at every sample, in any
  order, as many times as you like. This task is about restraint, not
  causality.
* Each row has 1 to 3 floats — the dimensionality varies per series and you can
  read it off the payload.
* Return a sorted list of integer indices. An index `i` means **sample `i` is
  the first sample of the new regime** (the boundary sits between `i-1` and
  `i`). Indices outside `[0, len(series))` are discarded; duplicates collapse.
* Return `[]` when you believe the series has no change points. That is a real
  answer, and on some series it is the right one.

The verifier imports this file and calls `find_changepoints` once per hidden
series. Nothing else about your file is inspected: helper functions, classes
and module-level constants are all fine.

## What changes at a boundary

One of four things, on a randomly chosen non-empty subset of the channels:

| kind | what moves |
| --- | --- |
| mean | the level shifts |
| variance | the scale is multiplied or divided by a factor |
| autocorrelation | the lag-1 dependence jumps, with the marginal variance held fixed |
| noise shape | the innovation distribution switches between light- and heavy-tailed, with mean, variance and autocorrelation all held fixed |

Magnitudes vary from blatant to genuinely subtle. A detector that only watches
the mean is blind to three of these four.

## What you are not told

* **The number of change points.** It is not an argument, it is not in the
  payload, and it is not recoverable from the payload. It varies per series.
* Series length carries no information about the count — the two are
  uncorrelated by construction.
* The hidden split contains regimes that the dev sample does not: series with
  **no change points at all**, series with **many more change points than any
  dev series**, and series where **every** change is a variance change. Do not
  calibrate a fixed budget on dev; it will not transfer.

## Scoring

A predicted index counts as a hit if it lands within **TOL = 5 samples** of a
true change point. Matching is within a series, one-to-one, and greedy by
distance: all candidate (prediction, truth) pairs closer than the tolerance are
sorted by `(distance, true_index, predicted_index)` and walked in that order,
and a pair is accepted only if neither of its two endpoints has already been
matched. A cluster of five predictions around one true change point therefore
scores one true positive and four false positives.

Matches are pooled across all hidden series into `TP`, `FP`, `FN`:

```
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
reward    = f1 = 2 * precision * recall / (precision + recall)
```

Reward runs from 0.0 to 1.0. 1.0 is the natural maximum of F1, not a
reference solution's score.

### Hard gate on the null series

Several hidden series have no change points at all. Let

```
null_fp_rate = (predictions made on null series) / (number of null series)
```

If `null_fp_rate > 0.5` — on average more than one spurious change point per
two change-point-free series — **the reward is 0.0 regardless of F1**. Pooled
F1 already punishes false positives; the gate makes spraying predictions
categorically fatal rather than merely costly. `null_fp_rate` is reported in
the metrics either way.

Both extremes fail: returning `[]` everywhere scores 0.0 because recall is 0,
and returning everything scores 0.0 because the gate fires.

## Working locally

* `/app/dev_series.json` — 8 labelled dev series (`values` plus
  `change_points`, and a `changes` field naming the kind and magnitude of each
  boundary). Use it however you like.
* `python3 /app/run_dev.py` — scores `/app/solution.py` against those labels
  with the same matching and metric code the verifier uses, and prints
  per-series predicted vs true counts.
* The dev split is small and is **not** a preview of the hidden distribution.
  There are no null series in it and its counts are not representative.

The starter `/app/solution.py` is fixed-budget binary segmentation on the mean
that returns exactly 3 points for every series. It is there to be replaced: it
cannot return zero, it cannot return twelve, and it cannot see a variance
change.

## Environment

* Python 3.12, standard library plus numpy. CPU only, no network needed, no
  other packages available.
* Determinism: the harness seeds `random` and `numpy.random` before your code
  runs, so the same file always earns the same reward. Do not rely on entropy
  for behaviour.
* Keep the whole run under a couple of minutes for ~20 series of up to 1000
  samples; the verifier stops waiting after 7 minutes.

## Time budget

You have **60 minutes**. There is no warning before the deadline: when it
expires, `/app/solution.py` is collected exactly as it is on disk at that
moment. Keep the file importable and submittable at all times while you
iterate — a broken file at minute 59 scores zero no matter how good the idea
in it was.
